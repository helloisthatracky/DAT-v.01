# PreviewKit — руководство оператора

Как подготовить данные, запустить сборку и прочитать результат.
Архитектура, калибровка и принятые решения — в [README.md](README.md).

---

## 1. Требования к входным файлам

| Требование | Почему так |
|---|---|
| **Белый фон** | На нём построен весь композит. Матирования (вырезания объекта) в MVP нет — оно и не нужно, пока фон белый |
| **Объект целиком в кадре** | Обрезанный по краю рендер даст неверный bbox, и модель встанет неправильно |
| **Короткая сторона ≥ 1500 px** | Иначе будет апскейл. Он ограничен 2× и всегда попадает в лог предупреждением |
| **PNG / JPG / TIFF / WebP** | Альфа-канал используется, если он есть; если нет — прозрачность оценивается по белому фону |
| **Сферы материалов — отдельными файлами** | Кроп по содержимому и круглая маска делаются автоматически. Сфера на белой подложке — нормально |
| **Тень оставлять** | Контактная тень исключается из расчёта посадки, но остаётся в кадре. Специально удалять её не нужно |

Два ракурса одной модели дают главное превью с обоими видами: вертикальные ставятся рядом, горизонтальные — стопкой, масштаб общий, чтобы виды были сопоставимы.

## 2. Раскладка каталогов

Обязательной папки для ассетов нет — CLI принимает любые пути. Но рабочие файлы стоит держать **снаружи репозитория**:

```
C:\DAT\
  previewkit\            ← код, обновляется целиком
    preview_core\
    assets\              ← только тестовые фикстуры, не для работы
    tools\
  work\                  ← ваши данные
    12345\
      views\
        model_01.png
        model_02.png
      spheres\
        mat1.png … mat4.png
      job.json
    12346\
      …
    out\
      12345\             ← результат сборки
```

Почему не внутрь `previewkit\assets\`: там лежат фикстуры, которые едут вместе с кодом и нужны тестам. Рабочие рендеры там будут засорять `git status`, попадать в архивы и рискуют пропасть при переустановке. Та же логика сохранится и дальше — у Electron-оболочки будет свой рабочий каталог, и `preview_core` о нём знать не должен.

## 3. Два правила разрешения путей

Неочевидный момент, о который легко споткнуться:

| Способ запуска | Относительные пути считаются от |
|---|---|
| `build job.json` | **папки самого `job.json`** — текущий каталог не важен |
| `build --views ...` | **текущего каталога** |

Так задумано: задание должно быть переносимым вместе со своей папкой, а флаги вы набираете руками в конкретном месте. Если сомневаетесь — пишите абсолютные пути, они работают везде.

## 4. `job.json`

```json
{
  "job_id": "необязательный идентификатор",
  "model_id": "12345",
  "views": [
    { "url": "views/model_01.png", "angle": "three_quarter" },
    { "url": "views/model_02.png", "angle": "front" }
  ],
  "spheres": ["spheres/mat1.png", "spheres/mat2.png"],
  "brand_logo": null,
  "outputs": ["main", "secondary", "closeup"],
  "overrides": { "sphere_count": 4, "max_views": 2 }
}
```

| Поле | Обязательно | Что делает |
|---|---|---|
| `model_id` | да | Попадает в имена файлов: `12345_01_main.jpg` |
| `views` | да | 1–2 рендера. `angle` — свободная пометка для себя, на сборку не влияет |
| `spheres` | нет | Сферы материалов. Ставятся только на главное превью |
| `brand_logo` | нет | Логотип бренда, левый нижний угол |
| `outputs` | нет | Что собирать. По умолчанию всё три роли |
| `overrides.sphere_count` | нет | Сколько сфер ставить максимум |
| `overrides.max_views` | нет | Сколько ракурсов пускать в главное превью |

## 5. Команды

```powershell
# сборка по заданию
python -m preview_core build C:\DAT\work\12345\job.json -o C:\DAT\work\out\12345

# сборка без job.json
python -m preview_core build --views render_a.png render_b.png `
    --spheres mat1.png mat2.png mat3.png mat4.png `
    --model-id 12345 -o out\

# со своей спекой вместо встроенной
python -m preview_core build job.json --spec my-spec.yaml -o out\

# проверить готовое превью, собранное руками в Photoshop
python -m preview_core validate ready.jpg --role main

# диагностика окружения, если что-то не импортируется
python tools\doctor.py

# тесты
python tests\run_tests.py
```

После `pip install -e .` вместо `python -m preview_core` можно писать просто `preview`.

Первая строка вывода всегда показывает, какая спека применилась:

```
spec: C:\DAT\previewkit\preview_core\spec.yaml  (v0.2.0-draft, cfeb748ea3460065)
```

## 6. Что появится в выходной папке

```
out\12345\
  12345_01_main.jpg        главное превью: модель + сферы + логотип бренда
  12345_02_secondary.jpg   второе превью: один ракурс, без сфер
  12345_03_secondary.jpg   третье (если было два ракурса)
  12345_04_closeup.jpg     клоузапы фрагментов
  12345_05_closeup.jpg
  report.json              что получилось и какие проверки прошли
  job.json                 копия задания + версия и хеш спеки
```

Копия задания сохраняется намеренно: старое задание всегда пересобирается по своей версии спеки, даже если спека с тех пор менялась.

## 7. Как читать `report.json`

```json
{
  "model_id": "12345",
  "spec_version": "0.2.0-draft",
  "spec_digest": "cfeb748ea3460065",
  "detected": {
    "type": "H", "ratio": 1.74, "bbox": [48, 185, 784, 608],
    "shadow_ratio": 0.1321, "views": 1, "elapsed_s": 2.5
  },
  "results": [
    {
      "role": "main", "index": 1, "path": "…/12345_01_main.jpg",
      "status": "pass",
      "checks": [{ "id": "canvas_size", "status": "pass", "msg": "" }],
      "placements": [{ "kind": "sphere", "index": 0, "rect": [531, 39, 659, 167] }],
      "warnings": []
    }
  ],
  "warnings": [],
  "status": "ok_with_warnings"
}
```

| Статус | Значение |
|---|---|
| `pass` / `ok` | Все проверки пройдены |
| `warn` / `ok_with_warnings` | Файлы собраны, но что-то стоит посмотреть глазами |
| `fail` / `failed` | Превью нарушает правило гайда, отправлять нельзя |

`detected.type` — определённый тип модели: `V` вертикальная, `H` горизонтальная, `S` близкая к квадрату. От него зависит раскладка и куда встанут сферы.

Одиннадцать проверок: `canvas_size`, `bg_pure_white`, `guides_touch`, `guides_overflow`, `tl_zone_clear`, `br_logo`, `no_spheres_on_2_3`, `sphere_overlap`, `single_instance`, `no_frame`, `file_limits`.

## 8. Частые ситуации

| Что видно в логе | Причина | Что делать |
|---|---|---|
| `is below the 1500px canvas` | Рендер меньше холста | Перерендерить крупнее. Апскейл ограничен 2× |
| `no usable views` | Путь не найден или файл битый | Проверить правило из раздела 3 |
| `capped at 2x upscale, guides are not touched` | Рендер слишком мелкий, модель физически не дотягивается до направляющих | Перерендерить крупнее |
| `two views fill only … falling back to one view` | Два ракурса вместе получились бы слишком мелкими | Нормальное поведение. Хотите два — снимите ракурсы ближе по пропорциям |
| `only N of M spheres fit` | На холсте не хватило свободного места | Уменьшить число сфер или взять более компактный ракурс |
| `source crop (…) - confirm manually` | Клоузап выбран автоматически | Посмотреть глазами. Это предложение, а не решение |
| `model covers …% of the TL zone` | Модель перекрывает угол, где 3ddd рисует свои кнопки | Обычно допустимо, но стоит взглянуть |
| `ModuleNotFoundError` | Проблема окружения, а не данных | `python tools\doctor.py` |

## 9. Ограничения текущей версии

**Геометрия не подтверждена модерацией.** Валидатор проверяет соответствие нашей спеке, а не требованиям 3ddd. Прогон по 20 одобренным эталонам: 17 не проходят наши направляющие — наш отступ 2.6% против медианных 1.56% у эталонов. То есть собранные превью систематически теснее принятых. **Отправлять на модерацию имеет смысл 2–3 штуки как разведку, а не пачку.**

**Клоузапы — предложение.** Алгоритм ищет фрагменты, плотные по деталям. На резной или фактурной модели работает хорошо, на крупной гладкой поверхности может промахнуться.

**Логотип 3ddd не рисуется.** Зона под него резервируется. Если выяснится, что рисовать должны мы — это один флаг `draw_3ddd_logo` в `spec.yaml`.

**Только белый фон.** Входы на цветном или прозрачном фоне не поддерживаются — это отдельный этап (Э5).
